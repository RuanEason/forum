# 用户头衔（名牌）系统计划

## 目标

为论坛增加一套独立的用户头衔/名牌系统，用来展示“管理员”“活跃用户”“积极用户”“社区贡献者”等身份或荣誉标识。

这个系统只负责展示和运营，不替代现有权限系统。现有 `User.role` 继续用于权限判断，例如管理员后台访问、置顶帖子、删除内容等；头衔系统负责用户名前后的视觉标识。

## 现状梳理

项目当前已经具备这些相关基础：

- `User.role`：当前用于区分 `user` 和 `admin`。
- `User.experience`：当前用于经验和等级。
- `src/lib/experience.ts`：已有经验奖励和等级计算逻辑。
- 首页帖子流、帖子详情、视频帖、评论区、个人主页都会展示用户昵称和头像。
- `/app/api/app/*` 下还有移动端或 App 端接口，需要同步返回头衔数据。
- 后台已有用户管理和帖子管理页面，可以扩展出头衔管理模块。

## 设计原则

- 权限和展示分离：不要把“头衔”塞进 `role`。
- 管理员头衔自动来自 `role`，避免权限和展示状态不一致。
- 手动头衔和自动头衔都使用统一展示组件。
- 帖子流和评论区保持紧凑，个人主页展示完整头衔。
- 第一阶段先实现稳定可控的人工授予，第二阶段再做自动计算。

## 头衔类型

### 系统身份头衔

由系统字段推导，不需要手动授权。

示例：

- 管理员：`User.role === "admin"`

### 人工授予头衔

由管理员在后台手动发放或撤销。

示例：

- 社区贡献者
- 测试协助者
- 版务协助
- 创作达人
- 特邀成员

### 自动规则头衔

由用户行为数据计算产生。

示例：

- 活跃用户
- 积极用户
- 优质创作者
- 热心回复
- 元老成员

## 数据库设计

建议新增两个模型：`UserTitle` 和 `UserTitleAssignment`。

```prisma
model UserTitle {
  id          String   @id @default(cuid())
  key         String   @unique
  name        String
  description String?
  type        String   @default("manual") // system, manual, auto
  color       String   @default("gray")
  icon        String?
  priority    Int      @default(0)
  active      Boolean  @default(true)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  assignments UserTitleAssignment[]
}

model UserTitleAssignment {
  id          String   @id @default(cuid())
  userId      String
  titleId     String
  reason      String?
  featured    Boolean  @default(false)
  startsAt    DateTime?
  expiresAt   DateTime?
  createdById String?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  user        User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  title       UserTitle @relation(fields: [titleId], references: [id], onDelete: Cascade)

  @@unique([userId, titleId])
  @@index([userId, featured])
  @@index([titleId])
}
```

`User` 模型增加关系字段：

```prisma
titleAssignments UserTitleAssignment[]
```

## 后端模块计划

新增 `src/lib/userTitles.ts`，统一处理头衔逻辑。

核心职责：

- 查询用户人工授予头衔。
- 根据 `User.role` 自动生成管理员头衔。
- 过滤未开始或已过期头衔。
- 过滤已停用的头衔定义。
- 按优先级、主展示状态、创建时间排序。
- 给帖子、评论、用户资料接口提供一致的数据结构。

建议返回结构：

```ts
type PublicUserTitle = {
  key: string;
  name: string;
  type: "system" | "manual" | "auto";
  color: string;
  icon?: string | null;
  priority: number;
  featured?: boolean;
};
```

## API 计划

### 后台头衔管理

新增接口：

- `GET /api/admin/titles`：获取所有头衔定义。
- `POST /api/admin/titles`：创建头衔。
- `PATCH /api/admin/titles/[id]`：更新头衔。
- `POST /api/admin/user-title`：给用户授予头衔。
- `DELETE /api/admin/user-title`：撤销用户头衔。
- `POST /api/admin/titles/recalculate`：刷新自动头衔。

### 现有接口扩展

这些接口需要在用户对象里带上 `titles`：

- `GET /api/post`
- `GET /api/app/post`
- `GET /api/app/comment`
- `GET /api/app/user/profile`
- `GET /api/app/user/posts`
- 关注/粉丝列表接口

帖子详情由 `src/lib/post.ts` 查询，也需要扩展作者、评论作者、回复作者的 `titles`。

## 前端组件计划

新增：

```txt
src/components/UserTitles.tsx
```

组件职责：

- 接收 `titles` 数组。
- 支持紧凑展示和完整展示。
- 帖子流、评论区默认最多展示 1 到 2 个。
- 个人主页可展示完整列表。
- 根据 `color` 和 `type` 输出稳定样式。

建议样式：

- 管理员：红色或玫红，带盾牌图标。
- 社区贡献者：蓝色。
- 活跃/积极：绿色或青色。
- 创作者：紫色或靛色。
- 元老成员：琥珀色。

注意避免所有头衔都像商业会员标识，整体应更偏社区荣誉。

优先接入这些展示点：

- 视频帖详情：作者昵称旁边。
- 评论区：评论作者和回复作者昵称旁边。

后台接入：

- 在管理后台新增 `头衔管理` Tab。
- 用户列表中显示用户当前头衔。
- 用户行增加“管理头衔”操作。

## 自动头衔规则初版

第一版规则建议保守一点，避免误发太多。

| 头衔 | 建议规则 |
| --- | --- |
| 活跃用户 | 最近 30 天发帖数 + 评论数 >= 20 |
| 积极用户 | 累计评论数 >= 50 或送出点赞数 >= 50 |
| 优质创作者 | 累计发帖数 >= 20 且累计获赞数 >= 50 |
| 热心回复 | 累计评论数 >= 100 |
| 元老成员 | 注册超过 365 天 |

自动头衔刷新方式：

1. 第一阶段：管理员在后台手动点击“刷新自动头衔”。
2. 第二阶段：如果后续项目引入定时任务，再做每日自动刷新。

## 验收清单

- 管理员用户自动显示“管理员”头衔。
- 普通用户不会因为有头衔获得管理员权限。
- 管理员可以在后台给用户授予和撤销人工头衔。
- 过期头衔不会展示。
- 停用头衔不会展示。
- 首页、详情页、评论区、个人主页展示一致。
- App 接口返回的数据结构和 Web 使用的数据结构一致。
- `npm run lint` 通过。
- `npm run build` 通过。

## 风险和注意事项

- 不要把头衔写死在多个组件里，应统一使用 `UserTitles`。
- 不要用 `role` 存放社区荣誉，否则后续权限会变混乱。
- 自动头衔规则不要一开始做得太复杂。
- 头衔过多会影响帖子流可读性，列表场景应限制展示数量。
- Prisma Client 输出目录是 `src/generated`，修改 schema 后需要运行 `npx prisma generate`。
