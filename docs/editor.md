# Editor 设计与开发规划

## 文档定位

这份文档以“最终确认方案”为准，用来指导论坛项目的 `/editor` 编辑器继续落地。

- 编辑器定位为独立的桌面端 Markdown 工作台
- 第一阶段不新建“文档”内容模型，直接复用现有草稿与发布体系
- 编辑器核心目标不是做完整文件管理，而是做沉浸式单文件写作体验
- 本文档优先描述可落地方案，不保留讨论过程中的分叉版本

---

## 一句话目标

把 `/editor` 做成一个仅限桌面端访问的、基于现有 `draft` 能力的单文件 Markdown 编辑器，体验接近轻量 VSCode 工作台，但最终仍发布为论坛里的 `TEXT` 类型帖子。

---

## 当前结论

### 内容模型

- 第一版将“文档”视为 `TEXT` 类型帖子
- 标题使用 `Post.title`
- 正文使用 `Post.content`
- 发布继续走现有草稿发布接口
- 不单独新增 `Document` 表，不拆新内容系统

### 路由与布局

- 编辑器入口为独立路由：`/editor`
- 编辑器需要弱化或隐藏全站外壳，避免 `Navbar / Ad / Footer` 打断工作台体验
- 当前项目已经通过 `RouteChromeController` + `body.editor-route` 的方式，对 `/editor` 路由隐藏了全站 chrome
- 因此短期内不强制要求新建 route group layout，先沿用现有方案即可

### 设备策略

- `/editor` 仅面向桌面端
- 小屏设备不进入正式编辑器
- 手机端访问时先显示拦截提示，再自动跳转到 `/post/create`
- 推荐优先按屏宽判断，小于 `1024px` 视为不可进入编辑器

### 编辑器定位

- 每次只编辑一个文档
- 不做文件树
- 不做多标签页
- 左侧只处理“历史草稿 / 当前文档 / 基础提示”
- 重点提升写作、保存、发布、结构导航体验

## 与现有项目的衔接

### 已有能力，直接复用

- 草稿创建：`POST /api/drafts`
- 草稿列表：`GET /api/drafts`
- 草稿详情：`GET /api/drafts/[id]`
- 草稿更新：`PATCH /api/drafts/[id]`
- 草稿删除：`DELETE /api/drafts/[id]`
- 草稿发布：`POST /api/drafts/[id]/publish`
- Markdown 标题提取：`src/lib/markdown.ts`
- 标题目录转换：`src/lib/catalog.ts`

### 当前代码现状

- 已存在入口页：[src/app/editor/page.tsx](/e:/website/src/app/editor/page.tsx:1)
- 已存在编辑器路由全站外壳隐藏逻辑：[src/components/RouteChromeController.tsx](/e:/website/src/components/RouteChromeController.tsx:1)
- 已存在对应样式入口：[src/app/globals.css](/e:/website/src/app/globals.css:65)
- 但核心工作台组件 `EditorWorkspace` 目前还未真正落地，`src/components/editor/` 目录也尚未建立

### 现有接口约束

- 文本草稿最大正文长度：`10000`
- 标题最大长度：`200`
- 文本帖子最多图片：`10`
- 文本帖子最多附件：`5`
- 发布前草稿必须处于 `READY`
- 发布成功后，当前草稿会被删除，不保留已发布草稿

这意味着编辑器第一版必须遵守现有发帖系统的边界，不能在 UI 上暗示“无限长文档”或“独立文档归档”能力。

## 产品方案

### 页面结构

### 顶部栏

- 左侧显示：
  - 可点击的文档标题菜单
  - 草稿状态
  - 最近自动保存时间
  - 标题菜单支持：
    - 保存草稿
    - 导入 Markdown
    - 导出当前正文 Markdown
    - 最近 5 条历史草稿与全部历史入口
- 右侧显示：
  - 蓝色 `发布` 按钮

说明：

- 标题菜单悬停约 700ms 后打开，点击标题可立即打开
- 菜单支持点击外部或按 `Escape` 关闭
- 导出文件使用当前内存中的正文，文件名取文档标题并清理非法字符

### 左侧栏

左侧栏只处理当前文档相关的素材与属性，不承载历史草稿列表。

- 图片池
- 帖子属性

历史草稿从顶部文档菜单进入：

- `历史草稿` 子菜单展示最近草稿
- `全部历史草稿` 打开独立历史面板
- 在历史面板中点击草稿切换到指定 `draftId`
- `新建文档` 同样位于顶部文档菜单

### 主编辑区

- 顶部单独的标题输入区
- 下方大面积 Markdown 编辑区
- 视觉风格偏工作台，不沿用普通发帖页卡片式布局
- 推荐特征：
  - 等宽字体正文
  - 舒适留白
  - 深浅分层背景
  - 当前行高亮
  - 行号支持

说明：

- 第一版不要求一定上复杂编辑器内核
- 可以先在 `textarea` 基础上做工作台包装
- 如果现有 `SimpleMarkdownEditor` 逻辑可复用，建议抽取“插入 Markdown 文本”和“快捷键”逻辑，而不是直接复用整套 UI

### 右侧区域

第一版建议不做真正双栏预览，先放文档结构大纲。

- 根据 `src/lib/markdown.ts` 提取标题
- 实时生成当前文档目录
- 点击大纲项滚动到对应段落

### 底部状态栏

- `Markdown`
- 当前字数
- 标题数
- 自动保存状态
- 快捷键提示

## 交互设计

### 打开流程

桌面端访问 `/editor` 后：

1. 先进入初始化过渡页
2. 同时加载：
   - 当前草稿
   - 左侧历史草稿
   - 自动保存状态
   - 标题大纲初始数据
3. 准备完成后，编辑器主体淡入

建议文案：

- 主文案：`正在为你打开编辑器，请稍等`
- 副文案：`正在完成编辑器初始化...`

### 初始化动画建议

建议做成“编辑器正在启动”的感觉，而不是普通 loading。

- 居中显示一个小型编辑器窗口轮廓或品牌块
- 显示前端节奏控制的进度条
- 背景轻微模糊，从站点态过渡到工作台态
- 数据准备好后，工作台淡入显示

### 空白态

空白态不要过度教程化，风格更像内置引导。

建议示例文案：

- `# 输入标题开始写作`
- `## 创建章节，右侧会自动生成目录`
- `Ctrl/Cmd + B` 加粗
- `Ctrl/Cmd + K` 插入链接

后续可扩展：

- `/table`
- `/code`
- `/quote`

### 快捷键

第一版就值得支持：

- `Ctrl/Cmd + S`：保存草稿
- `Ctrl/Cmd + Enter`：发布
- `Tab`：保留缩进体验

可后续补充：

- `Ctrl/Cmd + B`
- `Ctrl/Cmd + I`
- `Ctrl/Cmd + K`

### 草稿切换

- 点击左侧历史草稿时切换到对应 `draftId`
- 如果当前内容有未保存修改，先自动保存，再切换
- 若当前为空白且未生成草稿，可直接切换

### 发布

- 点击 `发布` 前，如有未保存修改，先补一次保存
- 发布成功后跳转帖子详情页
- 若接口返回不可发布状态，要明确展示原因

### 预览

- 第一版先做禁用占位
- 视觉上保留按钮与布局
- 第二阶段再做真正分栏预览

### 移动端拦截

手机端访问 `/editor` 时：

- 显示拦截页
- 文案：
  - `编辑器暂不支持手机端访问`
  - `即将为你跳转到普通发帖页面`
- 1 到 2 秒后执行 `router.replace("/post/create")`

## 视觉方向

### 总体气质

- 更像工作台，不像社区发帖表单
- 降低“卡片盒子感”
- 强化编辑区的沉浸感和专注感

### 建议视觉元素

- 浅灰蓝或冷灰背景，不要直接用纯白站点背景
- 标题区与正文区清晰分层
- 面板边界细、轻
- 主编辑区字体建议继续使用等宽字体变量
- 状态栏可做低饱和蓝色或石板色

### 不建议

- 直接复用普通发帖页布局
- 把编辑器塞进站点标准内容容器里
- 过度依赖大圆角卡片和表单式控件堆叠

## Markdown 渲染抽离建议

第二阶段做预览前，建议先抽一个公共渲染器。

可新增：

- `src/components/markdown/MarkdownRenderer.tsx`

抽离来源：

- 当前帖子详情页中的 `react-markdown + remark-gfm + remark-breaks + heading id` 逻辑

目的：

- 给未来编辑器预览直接复用
- 避免帖子页和编辑器页的 Markdown 渲染不一致

## 数据流建议

### 初次进入

- 若 URL 带 `draftId`，优先加载该草稿
- 若未带 `draftId`：
  - 可先创建空白状态，不立即创建草稿
  - 当用户开始输入后再创建草稿

### 自动保存

- 延续当前发帖页“延迟自动保存”的模式
- 建议 2 到 3 秒防抖
- 自动保存目标为 `persistMode: "SAVED"`

### 新建文档

- 清空当前编辑状态
- 如果当前已有未保存内容，先触发保存
- 新文档开始编辑后再创建新草稿

### 历史列表来源

- `GET /api/drafts?persistMode=SAVED&limit=50`

### 发布

- 先执行保存
- 再调用 `POST /api/drafts/[id]/publish`
- 成功后跳转 `/post/[postId]`

## 风险与注意事项

### 1. 现有草稿模型不是文档系统

风险：

- 发布后草稿会被删除
- 文档没有独立版本历史
- 不适合作“长期知识库”

结论：

- 第一版接受这个限制
- 如果未来想做真正文档系统，再单独升级模型

### 2. 内容长度限制

当前正文上限是 `10000` 字符。

风险：

- 超长文章会触顶

建议：

- 第一版先遵守限制
- UI 中适当展示字数信息
- 如后续确实需要长文档，再单独调整 `src/lib/draft.ts`

### 3. 不建议直接复用 `SimpleMarkdownEditor` UI

原因：

- 该组件服务于轻量发帖
- 已在多个业务场景复用
- 直接大改会影响现有页面

建议：

- 新编辑器单独做工作台 UI
- 必要时仅抽取其中的 Markdown 插入逻辑与快捷键逻辑

### 4. 不建议第一版引入过重编辑器内核

原因：

- 当前目标是尽快把桌面工作台体验做出来
- 现有接口和数据结构已足够支撑基础版本

建议：

- 第一版优先 `textarea + 工作台外壳 + 草稿系统`
- 后续若需要更强的块级能力，再评估升级编辑器内核

## 最终定义

`/editor` 第一版的正式定义如下：

- 一个仅限桌面端访问的独立 Markdown 编辑器
- 一个基于现有 `draft` 系统运行的单文件工作台
- 一个优先保证“写作沉浸感”和“保存发布闭环”的产品
- 一个暂不承担“文档系统”“多文件管理”“长期版本管理”的编辑器

这就是后续实现时应遵守的基准版本。
